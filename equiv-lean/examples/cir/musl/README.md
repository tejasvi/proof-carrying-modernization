The proofs are in `EquivLean/Demo/Cir/Musl/`. The generated Lean is in `EquivLean/Demo/Cir/Musl/Gen/`.

## Generation (`gen.sh MUSL_DIR SCRATCH_DIR`)

Compilers:
- `clang` is the pinned upstream ClangIR build (`~/cirlean_work/toolchain/upstream-4955d32b`).
- `cir2lean` is cirlean 28e2380's (`~/equivlean_work/vendor/cirlean-28e2380`), the pin when this Lean was generated. The proofs are checked at the current pin, cirlean e6ac99a.

The clang command is musl's own build line (`CFLAGS_ALL` in its Makefile):

    clang -fclangir -emit-cir -Xclang -fno-clangir-call-conv-lowering -O0 -std=c99 -nostdinc -ffreestanding \
      -D_XOPEN_SOURCE=700 -Dstrlen=musl_strlen -Dmemcpy=musl_memcpy \
      -I$MUSL/arch/x86_64 -I$MUSL/arch/generic -I$MUSL/src/include -I$MUSL/src/internal \
      -I$SCRATCH/obj/include -I$MUSL/include  FILE.c -o FILE.cir
    cir2lean FILE.cir EquivLean.Demo.Cir.Musl.Gen.<Name> EquivLean/Demo/Cir/Musl/Gen/<Name>.lean

- The renames are necessary. cirlean's frontend attaches its `strlen` / `memcpy` models to any function with those names, so musl's bodies would never run.
- The architecture is x86_64 (LP64), as in cirlean. clang defines `__GNUC__`, so musl's word-at-a-time paths are compiled in.

## What is proved, and the scope

cirlean has no byte-level memory. A value of a scalar type is stored per array element, and a pointer converted to an integer is a fixed encoding of block and path: `(uintptr_t)&x[i] % 4` (or `% 8`) is `(i + 1) % 4` (or `% 8`).

Up to cirlean 28e2380 (266d1ed), a `size_t` or `uint32_t` load or store at a `char` element read or wrote that one element: `loadTy` and `storeTy` only checked that the value fits. So musl's GNU word-at-a-time C (the `__may_alias__` words) had a meaning in cirlean that is not the machine's.

This finding led to cirlean's punning2 (2d65713). From the pin e6ac99a on, a scalar load or store whose type does not match the element it reaches is undefined (`Mem.punnedAccess`). GCC defines musl's word accesses through `__may_alias__`, but cirlean's typed memory treats them as type-punned accesses. So musl's word paths are undefined behaviour in cirlean: a run that reaches them has no outcome. The contracts below cover the byte paths. Each one states that the arrays it reads or writes are `char` arrays (`∃ es tlen, ty = .array (.int es 8) tlen`, either signedness); their conclusions did not change.

- `strlen`, refinement: `musl_strlen_refines` covers a C string in a `char` array block where every character up to the NUL is a `char` value. There, if musl's `strlen` returns, it returns the model's result, with no change to the caller's blocks. The runs that return are the byte path: they find the NUL in the alignment loop.
- `strlen`, the word path: `musl_strlen_aligned_ub`. From an 8-aligned position (`(i + 1) % 8 = 0` in cirlean's pointer encoding), musl's `strlen` goes straight to the word loop, whose `*w` is a `size_t` access to a `char` element. The run has no outcome, while the model returns the string's length.
- `strlen`, finding: `musl_strlen_nonchar_ub`. The model accepts any `int` elements, but musl's `char` loads are UB outside `-128..255`.
- `memcpy`, counterexample: `musl_memcpy_ne_model` (`MemcpyCex.lean`).
  - Copy the 7 characters `1 .. 7` into 7 zeros, both pointers at index 0. The model copies all seven.
  - After the head loop's 3 bytes, musl's `n & 4` copies a word through `uint32_t` pointers at a `char` element. That is a type-punned access, so musl's run has no outcome (`musl_memcpy_cex_ub`).
  - Up to 28e2380, musl instead left `1 2 3 4 0 0 0`.
- `memcpy`, refinement: `musl_memcpy_refines` (`MemcpyRefines.lean`; musl's run is `musl_memcpy_pspec` in `Memcpy.lean`). It covers `n` characters between two `char` arrays in different blocks, where:
  - musl's word paths do not run (`WordFree`): after the head loop's bytes, fewer than 4 are left with `d` 4-aligned, or fewer than 32 otherwise;
  - every source character is a `char` value, and is in `0 .. 127` if the destination is `signed char`.

  There, musl returns the model's result with the model's memory effect. Arrays of other element types are out of scope: in cirlean, musl's `unsigned char` pointers step one element at a time, whatever the element type.
- `memcpy`, model-vs-implementation differences (`MemcpyFindings.lean`), each a theorem on a concrete input:
  - `memcpy_diff_signed`: the `char` -56 (byte 0xC8) copied into a `signed char` array. musl stores the `unsigned char` value 200, while the model converts to the destination's type (-56). A later `char` load reads -56 from either.
  - `memcpy_diff_indeterminate`: an indeterminate source byte. The model copies it, but musl's `unsigned char` load is UB (`musl_memcpy_undef_ub`).
  - `memcpy_diff_overlap`: `memcpy(&x[1], &x[0], 2)` on `1 2 3`. musl copies forward byte by byte (`1 1 1`), while the model copies the original values (`1 1 2`). C makes an overlapping `memcpy` undefined (`restrict`), so the model's missing overlap check is a gap in the model itself.
