# JimpleLean

A formal specification of Soot's **Jimple** intermediate representation in Lean 4 (core Lean
v4.35, no Mathlib), with library models over native Lean types, a verification-condition
generator proved sound against the semantics, and automation that proves Java methods from the
Jimple that Soot produces for them.

Jimple is a typed, stackless, 3-address code: no operand stack, but every class, interface,
field and method signature and every exception handler of the bytecode is kept. Proofs are
about this representation, not about JVM bytecode.

```lean
import Jimple
open Jimple

jimple_import "examples_java/basics/jimple" as B      -- Soot output → `B.prog : Program`

/-- The method of class `cls` named `name`. -/
def mref (P : Program) (cls name : String) : MethodRef :=
  ⟨cls, ((P.classes.find? (·.name == cls)).bind fun d => d.methods.find? (·.name == name)).get!⟩

def maxSpec : Spec := Spec.of
  (fun args _ => ∃ a b : I32, args = [.int a, .int b])
  (fun args _ r _ => ∀ a b : I32, args = [.int a, .int b] →
     ∃ x : I32, r = some (.int x) ∧ x.toInt = max a.toInt b.toInt)

theorem max_ok : MethodVC B.prog (fun _ => none) 0 (mref B.prog "Basics" "max") maxSpec [] 20 := by
  jverify

theorem max_sat : Sat B.prog (mref B.prog "Basics" "max") maxSpec := max_ok.sat
```

`Sat` says that every terminating execution of `Basics.max` (big-step semantics `MExec`) from
a state satisfying the precondition ends in an outcome satisfying the postcondition.

## Building

```
lake build            # the library (Jimple)
lake build Examples   # the worked examples; every theorem is checked by the kernel
lake build jimple-run # native interpreter for .jimple directories (testing)
```

Build with one thread and `-DElab.async=false` (set in `lakefile.toml`) when memory is limited.

Jimple for your own code (JDK 17, Soot 4.7.1):

```
javac --release 8 -d classes src/*.java
java -cp soot-4.7.1-jar-with-dependencies.jar soot.Main \
     -cp classes -process-dir classes -pp -allow-phantom-refs -f J -d jimple
```

`jimple_import "jimple" as Foo` (relative to the package root) parses every `.jimple` file of
the directory at elaboration time and defines `Foo.prog : Program` and one constant per method
body (`Foo.Hello.«total(java.util.List)»`).

## The intermediate representation

`Stmt` has exactly Soot's 15 statement forms: `nop`, `breakpoint`, `identity` (`r0 := @this`,
`@parameterN`, `@caughtexception`), `assign`, `enterMonitor`, `exitMonitor`, `goto`, `ifGoto`,
`invoke`, `tableSwitch`, `lookupSwitch`, `ret`, `returnVal`, `returnVoid`, `throw`. Expression
operands are immediates (locals or constants); expressions are binary and unary operations,
casts, `instanceof`, `new`, array creation, field and array accesses and the five invoke kinds
(`virtual`, `special`, `interface`, `static`, `dynamic`). A method body is its typed locals, its
statement array and its trap table `(exception class, begin, end, handler)`. Classes keep their
superclass, interfaces, modifiers, fields and methods with full signatures, so overriding,
interface dispatch and exception matching are decided by the semantics.

## Semantics

* A state is a heap of objects, static fields, class initialization states, monitors and the
  text printed on `System.out`.
* `step` executes one statement in the request monad `Res`: a call to an application method is
  a request answered by the caller's semantics, an unspecified choice is a `Res.choose`. The
  relations `MExec` (method body), `VExec` (virtual call), `RExec` and `BExec` (body from a
  statement) are the specification; outcomes are `normal`, `exc` (uncaught exception) and
  `wrong`.
* Method selection follows the JVMS, including maximally-specific default methods.
  Exceptions raised by the JVM (`NullPointerException`, `ArithmeticException`,
  `ArrayIndexOutOfBoundsException`, `ClassCastException`, `NegativeArraySizeException`,
  `ArrayStoreException`, ...) are allocated as objects and dispatched through the trap table by
  the class hierarchy. Class initialization is lazy, in JLS 12.4 order (superclasses and
  superinterfaces with default methods first), and a failed initializer leaves the class
  erroneous (`NoClassDefFoundError`).
* `int`/`long` arithmetic wraps around exactly as in Java; `float`/`double` are exact IEEE-754
  values (every operation rounds the exact rational result).
* What the JDK leaves unspecified is nondeterministic: identity hash codes, iteration order of
  hash-based collections, `==` between distinct strings, boxes and decimals with equal contents.
* What is not modelled is `wrong` (no library model, reflection, ...). Contracts written with
  `Spec.of` exclude `wrong`, so a proof also shows that the code stays within the model.

## Library types as Lean types

| Java | Lean |
|---|---|
| `int`, `long`, `char`, ... | `BitVec 32/64` (`I32`, `I64`); `toInt` gives the value in `ℤ` |
| `String`, `StringBuilder` | `JStr = List (BitVec 16)` (UTF-16 code units) |
| `BigDecimal` | `BigDec` (unscaled `ℤ`, scale `ℤ`); `toRat : BigDec → ℚ` is its value |
| `BigInteger` | `ℤ` |
| `List` (`ArrayList`, `LinkedList`, `List.of`) | `List Value` |
| `Map` (`HashMap`, `LinkedHashMap`, `TreeMap`) | `List (Value × Value)` |
| `Set` (`HashSet`, `LinkedHashSet`, `TreeSet`) | `List Value` |
| boxed primitives, `RoundingMode`, `MathContext` | `Value`, Lean enumerations and structures |

`docs/LIBRARY_MODELS.md` lists the 449 modelled constructors, methods and fields (generated
from `Native.lean`). `DecimalLemmas.lean` states every `BigDecimal` operation in `ℚ`
(`toRat_add`, `toRat_mul`, `setScale`/`divide` with each rounding mode as rounding of the exact
quotient, `compareTo` as the order of `ℚ`), so contracts can be written in plain rational
arithmetic: `Examples/Invoice.lean` proves that a loop over a `List<Priced>` returns
`Σ price(x)` in `ℚ`.

## Contracts and verification conditions

* `Spec.of pre normal exc`: precondition on the arguments and the entry state; postconditions
  for normal return and for an uncaught exception. Ghost variables are existentials in `pre`
  and universals in the postconditions.
* `Sat P m S`: partial correctness of method `m`. `Valid P Γ`: every contract of the table `Γ`
  holds for its method and for every application class overriding it (behavioural subtyping).
* `MethodVC P Γ d m S A fuel`: symbolic execution of the body of `m`, with loop invariants `A`
  (assertions at statement indices) and calls answered by the callee's contract in `Γ` or by
  inlining (depth `d`).
* Soundness: `AllVC.valid : AllVC P Γ d Ann → Valid P Γ`; for whole programs
  `Contracts.valid`, for methods that only call the library `MethodVC.sat`.
* Linking: `MethodVC.sat_of_valid : Valid P Γ → MethodVC P Γ d m S A fuel → Sat P m S` and
  `ContractVC.ok : Valid P Γ → ContractVC P Γ d Ann sig S → ContractOK P sig S` let each
  method be proved once, against its callees' contracts only (call cycles go through
  `Contracts.valid`). A contract of a static method (`P.staticDecl sig`) owes nothing to
  subclasses; one of an instance method holds for every application class implementing it.
  `Examples/Linking.lean` proves `Priced.price` and `Hello.total` separately and links them.
* Per-method proofs: `BodyVC F Γ d m S A fuel` is `MethodVC` for every program that satisfies
  the lookup facts `F`, so the proof depends only on the method's own class module and the
  contracts. Import one class per module (`jimple_import "C.jimple" as HC`, which also defines
  `HC.C.«m(sig)».ref`), state `F := (Contains · [HC.C])` (the program contains the class and
  shadows no library class; finer per-lookup facts come from `jfacts`), prove with
  `jverify_body`, assemble with `jimple_program HA HB … as Whole`, and link with `BodyVC.sat`
  (`Contains.of_check`, by evaluation). A contract follows from the linked proofs of the
  methods it covers: `jcontract_ok [sat₁, …]` proves `ContractOK P sig S` by enumerating the
  program's classes, discharging abstract and unrelated classes and using the given `Sat`
  facts (static methods, interfaces, virtual methods); see `Examples/Caching/`.
* Method-level proofs: `jimple_method "C.jimple" "m(T1,T2)" as HM` imports one method
  (`HM.C.«m(T1,T2)».ref`), `jimple_shape "C.jimple" as HS` the class without method bodies
  (`ClassDecl.erase`). With the facts `Shapes P [HS.C, …]` (no shadowing, and each class of `P`
  erases to its shape) a body proof depends on its own body, the shapes and the callee
  contracts only: editing another method's body (keeping its contract) changes none of its
  inputs. Methods of shaped classes found during the proof have unknown bodies, so calls to
  them go through contracts. At link time `Shapes.of_check` checks the shapes by evaluation.
  `Examples/Methods/` proves `Calc.sumSq` once and links it into the program and into a variant
  with another body of `Calc.add`.
* Termination (`docs/TERMINATION.md`): `MTerm P m args σ`, every execution of the call terminates
  and one exists. `TermVC.mterm` proves it from a termination VC (a variant per loop cut point, the
  callees' termination by their contracts, in rank order); `TermVC.of_thin` builds that VC from the
  method's `MethodVC` and a thin VC that checks only the variants and that no call is stuck. With
  `Sat`, `total_of_sat_mterm` gives total correctness: an outcome exists, and every outcome
  satisfies the contract.
* Contracts that mention the program, such as the generic contracts below, use
  `BodyVCP F Γ d m S A fuel` (`Γ P`, `S P` taken in each program) and `jverify_generic_body`.
  Such a proof does not look at the rest of the program, however large: on commons-lang3
  (675 classes) a method's generic contract checks in seconds against its class module, where
  the same proof on the whole program timed out. Objects whose class is only known to be a
  subclass of `C` (an argument of type `C`, `this`) have the fields `C` declares, typed
  (`fields_of_sub`), so field accesses work without knowing the subclasses.

## Automation

* `jverify [defs]` proves `MethodVC` goals: it executes the body symbolically through the
  semantics (simp set `jsimp`), evaluates program-structure lookups in the kernel (statement
  fetch, class lookup, subtyping, method selection, trap search), runs the library models,
  splits at branches and exceptional paths, and closes the leaves with `omega`, `grind`,
  `bv_decide` and `decide`. Along the way it destructures hypotheses, instantiates quantified
  facts and collection quantifiers, unifies facts about the same heap cell, removes
  overflow-free wraparound and states decimal comparisons and remainders as integer facts.
* `jvc [defs]`: the same loop on any goal. `jcontracts [defs]`: a whole contract table, with
  call targets and implementing classes enumerated.
* The user writes the contracts, the loop invariants and the list of definitions to unfold.
  Domain lemmas tagged `@[jsimp]` are used automatically.
* Large methods: callee contracts are unfolded only where they are applied (`jspec`), and the
  method's cut list and postcondition are folded into local functions during symbolic execution
  (`jFoldCuts`), so each step carries neither. Lists of heap strings (output lines, the contents
  of a `List<String>`) are stated with `StrsAt σ ys ss`; such a fact about an earlier state
  carries over to a later one through `StrMono` (`jStrsMono`); so do facts and values tagged
  `@[jframe]` (e.g. a record predicate and its display line, kept `@[irreducible]`), through the
  heap agreement `Agree σ σ'` (`jFrameStep`). A method with a loop can be
  checked as one lemma per segment, run in parallel: the entry path and each case at the loop
  head, with the invariant's variables as parameters (`Examples/CardDemo/Cbact02cRun*.lean`,
  assembled into `MethodVC` in `Cbact02cRunVC.lean`).
* Contracts on abstract states, with `set_option jimple.modelContracts true` (off by default; off,
  `jvc` behaves as in snapshot 20261024T2110Z). A representation relation `R σ x s` between an
  object and a model value: a precondition `∃ g, R σ x g ∧ …` takes the witness `g` from a hypothesis that
  unifies with the conjunct (`jExists`, also equations with a known left side), and a
  postcondition `∀ g, R σ x g → …` is instantiated against the hypotheses (`jForward`). Call
  such a method at a cut point of its own, with `R` kept folded there
  (`attribute [local irreducible] R`): its premises are then hypotheses of the call's state. Frame
  lemmas tagged `@[jframe]` may take any frame relation `F σ σ'` as premise: a hypothesis states
  it (a callee's frame) or it is unfolded and left to the loop. Heap facts of a later state are
  carried back through a callee's frame rule (`jFrameInst`), and an address comparison is refuted
  from the two objects' contents (`jne_heap`, in the discharger) instead of split on.
  The hypotheses' conditional rewrites are discharged as the goal's, and the cut facts and the
  postcondition stay folded until a cut or a return.
* String concatenation (`invokedynamic makeConcatWithConstants`) runs with literal recipes (same
  option: the simp set `jsimpc` and the simproc `jconcat`).
* `set_option jimple.trace true` reports where the automation stops (remaining goals are left
  to the user); `jimple.maxHeartbeats` bounds one call. With `jimple.debug` and
  `$JIMPLE_DEBUG_LOG` set, the phases of each step, the goals before slow steps (over 20 s) and
  the goals left over are written to that file as they happen (`jimple.dumpFuel n`: the goal
  before the step at loop fuel `n`). `jimple.hypHeapFacts` lets hypotheses be evaluated with the
  heap facts too (`argText`, `strOf` in invariants). `ite_nat_ne` (an address comparison refuted by
  the discharger) is not in `jsimp`: tried on every `if` over `Nat` it was costly on large
  methods; pass it to `jvc`/`jverify` where heap updates leave such comparisons.
* `jverify_generic` proves `genericSpec P m` with no input: from typed arguments and a typed
  state, the method returns or throws only what it declares, and never leaves the model. When
  it fails, the remaining goal is the bad input (e.g. a `null` field); `report` runs the method
  on such an input and prints the outcome with Java line numbers (Soot's `-keep-line-number
  -print-tags` output fills `Body.lines`).

## COBOL rewrites

`Jimple/Cobol.lean` gives COBOL numeric items (`Pic`: `PIC S9(i)V9(f)`), `MOVE`, `COMPUTE` with
and without `ROUNDED` and `ON SIZE ERROR`, `DIVIDE` and `REMAINDER` over `ℚ`, and proves that
the usual Java idioms implement them (`setScale`/`divide` with `HALF_UP` or `DOWN`, then a
range check; `remainder(10^i)` for high-order truncation). In `Examples/Mainframe.lean` the
contracts of the Java rewrite are COBOL statements and each proof is one `jverify` call.

## Validation

* Differential testing against the JVM (`tools/difftest.sh`, `docs/DIFFTEST.md`): 32 programs (Java 8,
  plus Java 17 records and JUnit 4/5 tests)
  (arithmetic, collections, `BigDecimal`, exceptions, nested classes, enums, interfaces,
  initialization order, recursion, ...) produce byte-identical output under the JVM and under
  the interpreter of the semantics. Three known differences are documented: JDK "helpful"
  `NullPointerException` texts (unspecified), a Soot typing bug, non-ASCII digits (`wrong`).
* Scale: Soot's Jimple for commons-lang3 3.14.0 (675 classes, 5,258 bodies, 51,525
  statements) parses without failures; `jimple_import` of all of it takes 26 s and 1.4 GB.
  Class lookups go through a hash index (logarithmic, also in the kernel). On 12 of its
  methods, `jverify_generic` proves 5 with no input (99 s for the file); of the rest, 3 throw
  `IllegalArgumentException` or fail on `null` by design, one needs callee contracts, one a
  class invariant of a static array, and two (with `Boolean` parameters) are open gaps.
* Libraries from bytecode: the JDK's `java.util.regex` (139 classes, converted by Soot) runs
  as program classes; regex programs and 35 commons-lang3 `StringUtils` methods match the JVM.

## Trusted base

The Lean kernel and the definitions that make up the specification: `Syntax`, `Numeric`,
`JString`, `Decimal`, `Value`, `Prelude`, `Program`, `Monad`, `Native`, `Semantics`, the
statements of `Logic`, and for termination `MTerm` (`Termination`). Not verified: `javac`, Soot,
and the `.jimple` parser. A theorem is about the `Program` term that `jimple_import` produced; the
differential tests run the same parser.

## Limitations

* `Sat` is partial correctness (it constrains terminating executions). Termination is a separate
  proof (`MTerm`, `docs/TERMINATION.md`), done here for `sumTo` and the three CardDemo programs.
* Single-threaded: monitors are modelled, threads are not.
* Not modelled (`wrong`): reflection, regular expressions, character sets and locales, I/O
  other than `System.out`, `String.format`, streams, conversion of `float`/`double` to text.
* Soot's front end is trusted (see the typing bug above); Java 8 bytecode (`--release 8`) is
  the tested input.
